# 灵感收集箱

这里用来暂存还没进入正式规划的想法、直觉、玩法脑洞和长期方向。

使用规则：

- 想法可以很粗糙，不需要一开始就写成任务。
- 每条想法下面预留 `Codex 评注`，我可以之后补充可行性、风险、拆分建议或相邻方案。
- `状态` 只用于轻量标记，不等同于 TODO。
- 真正要开工时，再把条目整理进 `TODO.md` 或对应设计文档。

状态建议：

- `inbox`：刚记下，还没评估。
- `watch`：值得保留，暂时不做。
- `candidate`：适合近期拆成任务。
- `planned`：已经进入正式规划。
- `closed`：暂时放弃或被别的方案替代。

## 模板

```markdown
## YYYY-MM-DD - 想法标题

状态：candidate

### 我的想法

这里写你的原始想法。可以是几句话，也可以只是关键词。

### Codex 评注

这条可以进入近期候选规划，因为现有系统已经有 `selfGuard.autoEat`、`lowFood`、`interact.eat` 和基础食物识别，离“稳定自动吃饭”并不远。

但它不能一次做成完整版本。比较稳的拆法是：

1. 先把现有自动进食统一到 `runtime.eatFood()`，不要继续在 self-guard 里直接 `bot.equip()` / `bot.consume()`。
2. 增加可配置的 `foodHotbarSlot`，默认第 9 格，让小狸吃饭前先把食物放到固定槽位。
3. 增加 `foodWhitelist`，默认只吃明确允许的食物；未知食物先问 owner / 白名单玩家。
4. 增加 `foodCheckIntervalMs`，让检查频率可配置，避免每 tick 都想吃东西。
5. 第二阶段再加入 vanilla 食物营养表，按“当前缺口 + 食物恢复值 + 饱和度”做低浪费选择。

你说的“空心/白色描边饱食度”大概率不是原版 Java 客户端直接显示的数值，而是 AppleSkin 或类似 HUD mod 对隐藏饱和度/食物预览的可视化。原版实际有三层：可见饥饿值、隐藏饱和度、隐藏消耗值。饱和度会先被消耗，耗尽后才掉可见饥饿值；食物恢复值吃超了会浪费，不会把溢出的饥饿值神奇转成更多饱和度。

近期实现时不要先追求“最优吃法”，先追求“别乱吃、能问人、危险时能保命”。也就是说，小狸先学会不吃奇怪蘑菇，再学会精打细算。这个顺序很重要。

### 可能落点

- 文档：`docs/idea-inbox.md`、后续可拆到 self-guard / food policy 设计文档
- 代码：`selfGuard.autoEat`、`interact.eat`、`ClientAdapter.eatFood()`、食物白名单配置、白名单回复监听
- 测试：低饥饿自动吃白名单食物、未知食物询问、无回复时求救、饥饿缺口与食物选择
```



## 2026-06-16 - 整合包知识与能力逐步成长

状态：watch

### 我的想法

第一次进入某个整合包时，读取 mod 列表，并去 MC百科、CurseForge 等地方查 mod 介绍。前期先像百科全书一样理解整合包内容；后期希望小狸真的会玩这些 mod，例如农夫乐事做菜、机械动力/精妙存储/精妙背包等容器或多步骤玩法。

### Codex 评注

这个方向很适合拆成两层：先做“知识索引”，再做“可执行技能”。知识索引用来解释 mod、物品、方块和配方；可执行技能需要依赖客户端能力、容器识别、GUI 操作和多步骤任务追踪。不要一开始就让 LLM 猜复杂工序，应该先把配方/容器/动作能力变成可验证的数据和工具。

### 可能落点

- 文档：`docs/modded-client-adapter-plan.md`
- 代码：mod 列表读取、mod 知识缓存、容器 capability 索引、技能执行器
- 测试：用一个小型整合包做只读索引验收，再做单个可执行技能验收



## 2026-06-16 - 云端大模型规划，本地小模型执行

状态：candidate

### 我的想法

后续项目变大以后，所有决策都用云端 API 可能性价比不高。希望高层规划、任务拆分、策略切换用云端好模型；本地跑一个小模型负责具体任务执行、短上下文判断或工具调用。

### Codex 评注

这个非常符合现在的分层方向：云端模型适合做“慢思考”和长期规划，本地模型适合做“短回路”和低成本执行。但要避免两个模型互相抢控制权。比较稳的路线是把它设计成 `strategist -> planner -> executor` 三层：高层只产出目标和约束，中层拆步骤，底层只能在白名单工具里执行并回报状态。

### 可能落点

- 文档：`docs/ai-control-architecture.md`、`docs/hierarchical-agent-framework.md`
- 代码：planner provider 抽象、本地 executor provider、预算/冷却/失败回退策略
- 测试：同一目标分别用 mock planner 和 mock executor 验证链路

## 2026-07-05 - 游戏和 TTS 共用小狸长期记忆

状态：candidate

### 我的想法

`C:\xiaoli` 下新增了 `voice` 目录，用来做小狸的 TTS 语音和后续直播接入。虽然这和当前游戏 bot 主流程不是一条线，但后续 TTS 的记忆应该和游戏这边的小狸记忆共通。因此可以考虑在 `C:\xiaoli` 下新增 `memory` 文件夹，把长期记忆从 `moony-mcbot` 项目内部迁出去。

### Codex 评注

这个方向是对的，而且应该尽早设计，但不应该立刻把现有 `chat-configs.json` 整体搬走。当前文件里混有 chat 配置、agent 配置、self-guard、territory、strategic goal 和 memory；其中只有玩家、地点、关系、偏好、经历摘要适合迁入共享记忆。

更稳的路线是先建立 `C:\xiaoli\memory` 作为长期记忆事实源，再做一个 `MemoryStore` 抽象。第一阶段双写：游戏侧继续写旧配置，同时写共享记忆；TTS 侧先只读共享记忆。等确认稳定后，再让游戏侧启动时优先读共享记忆，旧配置只作为 fallback。

这条线和当前 adapter/runtime 主线不冲突。它更像“人格连续性底座”：游戏里发生的事、直播里说过的话、Judy 的称呼和关系，都可以慢慢汇到同一个小狸记忆里。要小心的是不要把密钥、账号、access token、瞬时任务状态写进 memory。小狸可以记得茉莉喜欢什么，但不该记得密码，猫猫也要有职业操守。

### 可能落点

- 文档：`docs/shared-memory-plan.md`
- 代码：`MemoryStore`、`XIAOLI_MEMORY_DIR` / `MCBOT_MEMORY_DIR`、player/place/taskHistory 双写、episodes append-only
- 测试：旧配置 fallback、共享记忆优先读取、双写一致性、TTS 只读读取玩家别称和最近事件
